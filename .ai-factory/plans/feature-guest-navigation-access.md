## Задача одним абзацем

Установка научилась отдавать пункты навигации неавторизованному посетителю
двумя новыми операциями вместо одной прежней. Пакет обязан их звать: гостевую —
когда сессии нет, пользовательскую — когда есть. Сегодня на странице без сессии
`IdentityProps::share()` отдаёт пустой рейл и пустой список origin'ов для
политики содержимого, то есть гостю рейл не покажется, даже когда установка его
отдаёт.

## Зависимость от установки

Работа выполняется **против локально поднятого `identity-service`** ветки
`feature/guest-navigation-access` (фазы 0–5 там завершены). Опубликованная
установка новых адресов ещё не знает.

Подключение со стороны сервиса — `path`-репозиторий на этот клон; описано
в плане сервиса, раздел «Тандемный цикл».

## Новый контракт установки

| Было | Стало |
| --- | --- |
| `POST /api/users/services`, тело `{sub}`, область `users:read` | `POST /api/navigation`, тело `{sub}`, область `navigation:read` |
| — | `GET /api/navigation`, без тела, область `navigation:read` |
| Ответ `{sub, profile_url, logo_url, items}` | Пользовательский `{items, logo_url, profile_url}`, гостевой `{items, logo_url}` |

`sub` из ответа исчезает: он был эхом присланного. `profile_url` у гостя
отсутствует, и это значащее отсутствие — «страницы профиля у смотрящего нет».

Форма пункта (`NavItem`: `id`, `name`, `url`, `icon_url`, `order`)
**не меняется**.

  необязательное поле заставило бы каждого потребителя различать «не пришло»

  Разбор остаётся терпимым: отсутствующее поле → пустая строка, отсутствующий
  `items` → пустой список.
  **Логирование:** нет, DTO.

- [x] **3. Обращение без тела в `ServiceApiClient`**
  **Файл:** `src/Api/ServiceApiClient.php`
  Класс объявляет единственный метод `post()`, и в нём же живут повтор на
  `401 invalid_token`, чтение кода `error` и журналирование отказа. Гостевая
  операция идёт `GET` без тела, и **звать её нечем**: без этой правки
  исполнитель либо пойдёт мимо клиента через `IdentityHttp` — и потеряет повтор
  с обновлением служебного токена, — либо отправит `POST` с пустым телом.
  Завести `get(string $path, string $operation)`. Общее — отправка, повтор,
  разбор кода отказа и журналирование — обязано остаться **одним** закрытым
  путём; расходится только сама отправка: с телом и без.
  Докблок класса перечисляет `/api/users/resolve` и `/api/users/services`
  как единственное исключение из правила «адреса читаются из документа
  обнаружения» — перечень поправить здесь же.
  **Логирование:** прежнее по составу, приставка `[ServiceApiClient.get]`
  у своей ветви.

- [x] **4. Две операции в `NavigationClient`**
  **Файл:** `src/Api/NavigationClient.php`
  **Зависит от:** задачи 3 (транспорт без тела) и 6 (область `navigation:read`).
  Константа `PATH = '/api/users/services'` заменяется на `PATH = '/api/navigation'`
  — адрес один, различаются метод и наличие тела.
  Метод `for(string $sub)` зовёт `POST` с телом `{sub}`; новый метод
  `forGuest()` зовёт `GET` без тела. Общее — кэш, признак устаревания и
  обработка отказов — вынести в закрытый метод, чтобы правило жило один раз.
  Ключи кэша: пользовательский по `sub`, гостевой — единственный на установку.
  **Отметка состава в ключе поднимается с `v2` до `v3`.** Довод записан
  в докблоке `key()` и в этой правке действует буквально: состав записи
  изменился (ушёл `sub`), и разборщик 0.4, прочитав запись, положенную 0.3,
  молча деградирует. Поднять отметку обязательно — это не украшение.
  `staleOrEmpty()` перестаёт принимать `sub`.
  `404 user_not_found` остаётся отказом у пользовательской операции; у
  гостевой такого кода нет вовсе — адресата нет.
  **Логирование:** DEBUG `[NavigationClient.for] rail resolved` и
  `[NavigationClient.forGuest] guest rail resolved` с числом пунктов;
  WARN при недоступности — у гостевой без поля `sub`.

### Фаза 3 — Свойства продукта

- [x] **8. Гостевая ветка `IdentityProps::share()`**
  **Файл:** `src/Inertia/IdentityProps.php`
  Сейчас при `sub === null` возвращается `crossService` с пустыми `items`,
  `profileUrl` и `logoUrl` (строки 47–61). Заменить на вызов
  `NavigationClient::forGuest()`: `profile` остаётся `null`, `crossService`
  заполняется гостевым набором, `profileUrl` приходит пустым.
  Форма свойства не меняется — `profile` был nullable, `crossService` не был,
  и гостевой случай в неё уже вписан. **Гостевая ветка обязана возвращать ту же
  объявленную форму, а не сокращённую:** состав описан `@return array{...}`
  в докблоке метода, и расхождение поднимет `composer types:check`.
  Отказ установки не должен ронять страницу: пустой рейл — законное состояние
  (критерий 91).
  **Логирование:** DEBUG `[IdentityProps.share] guest props shared` с числом
  пунктов вместо нынешнего `no identity session`.

- [x] **9. Origin'ы иконок для гостя**
  **Файл:** `src/Support/IconOrigins.php`
  `forSession()` возвращает пустой список при `sub === null` (строка ~58), и
  докблок объясняет это тем, что «на запросе без рейла список пуст». **С
  гостевым рейлом посылка перестаёт быть верной**: изображения на такой
  странице есть, а origin'ов в политике содержимого продукта нет — обозреватель
  заблокирует все иконки, и проявится это только в его консоли.
  Гостевая ветка обязана читать `forGuest()` тем же способом, каким
  пользовательская читает `for($sub)`.
  Поправить **оба** докблока и журнальную запись: докблок метода обещает
  «origin'ы иконок текущего пользователя», а в DEBUG уходит `'sub' => $sub`,
  который у гостя равен `null` — вместо него признак гостя.
  В докблоке класса записать, откуда теперь берётся обещание «обращений
  к установке этот класс не делает»: у вошедшего его держала сборка свойств,
  положившая ответ в кэш, у гостя — **общая на установку запись гостевого
  кэша**, а не наличие сессии. На запросе, где `IdentityProps::share()`
  не вызывалась, первое обращение к установке пойдёт отсюда.
  **Логирование:** DEBUG с числом найденных origin'ов.

- [x] **10. Язык для гостя**
  **Файл:** `src/Inertia/IdentityProps.php`
  Добавить в свойства поле `locale` из `app()->getLocale()` продукта.
  **Зачем:** язык рейла у вошедшего берётся из профиля, а у гостя профиля нет,
  и `@verdeect/identity-nav-vue` откатывается на жёсткий `'ru'` — на
  англоязычной установке гостевой рейл выйдет русским. Язык гостя знает
  продукт (заголовок `Accept-Language`, кука, умолчание), а не установка:
  диктовать его она не вправе, потому что о госте не знает ничего.
  Расширить объявление `@return array{...}` полем `locale: string`: форма
  свойств задана докблоком, и без правки `composer types:check` свалится
  на несоответствии возвращаемого состава объявленному.
  Поле парное с задачей 3 плана `@verdeect/identity-nav-vue`; выпускать
  пакеты порознь нельзя.
  **Логирование:** язык в существующем DEBUG сборки свойств.
