# Встраивание в продукт

Четыре обязанности продукта: зарегистрировать middleware, закрыть экраны
входом, отдать данные интерфейсу и разрешить логотип установки политикой
содержимого.

## Приложение как BFF

Браузер получает сессионную куку; токены хранятся на сервере и наружу
не выходят никогда.

1. Интерфейс раздаётся **с того же источника**, что и приложение. Разнесение
   по доменам ведёт к ограничениям браузера на сторонние куки и к попыткам
   вынести токен в браузер.
2. Аутентификация **сессионная, не токенная**.
3. Защита от подделки межсайтовых запросов обязательна.
4. Поток входа полностью серверный: редирект на установку, приём ответа, обмен
   кода с PKCE, сохранение токенов, установка куки.
5. Обновление токена выполняется на сервере прозрачно для интерфейса.

## Middleware: порядок существен

```php
// bootstrap/app.php
use Verdeect\IdentityIntegration\Http\Middleware\EnforceSessionMarks;
use Verdeect\IdentityIntegration\Http\Middleware\RefreshIdentityToken;
use Verdeect\IdentityIntegration\Http\Middleware\RequireIdentitySession;

->withMiddleware(function (Middleware $middleware): void {
    $middleware->trustProxies(at: '*');

    $middleware->web(append: [
        EnforceSessionMarks::class,
        RefreshIdentityToken::class,
        HandleInertiaRequests::class,   // разделяемые свойства продукта
        ContentSecurityPolicy::class,   // политика содержимого продукта
    ]);

    $middleware->alias([
        'identity' => RequireIdentitySession::class,
    ]);
})
```

**Почему именно так:**

- `EnforceSessionMarks` идёт **первым**: гасить отменённую сессию нужно
  до того, как её токен пойдёт на обмен, — иначе продукт обменивал бы токены
  сессии, которой уже нет.
- `RefreshIdentityToken` — **вторым**: он поддерживает токен свежим до того,
  как разделяемые свойства пойдут за данными рейла. Обмен в начале запроса
  избавляет от отказа из середины отрисовки страницы.
- `RequireIdentitySession` вешается **алиасом** на группы маршрутов,
  а не в `web`: маршруты входа и обратного вызова обязаны оставаться
  доступными без сессии.

| Middleware | Что делает | Когда уничтожает сессию |
| --- | --- | --- |
| `EnforceSessionMarks` | сверяет возраст сессии с отметками по `sub` и `sid` | сессия помечена погашенной из установки |
| `RefreshIdentityToken` | держит токен доступа свежим, обменивает с упреждением | обмен не удался (`SessionExpiredException`) |
| `RequireIdentitySession` | закрывает экраны входом | не уничтожает, только отправляет на вход |

Сессию пакет уничтожает **штатным механизмом Laravel** — `invalidate()` плюс
`regenerateToken()`. Прямого доступа к хранилищу сессий у него нет: это
привязало бы пакет к драйверу.

## Маршруты

Пакет регистрирует три маршрута сам, в группе `web`:

| Маршрут | Имя | Назначение |
| --- | --- | --- |
| `GET /auth/login` | `identity.login` | начало потока кода с PKCE |
| `GET /auth/callback` | `identity.callback` | приём ответа установки |
| `POST /auth/logout` | `identity.logout` | выход через `/end-session` |

Выход — `POST`, а не `GET`: по ссылке из письма или чужой страницы выход
вызвать нельзя.

Объявлять эти маршруты в продукте не нужно. Закрывать их алиасом `identity`
тоже: вход обязан работать до появления сессии.

## Закрытие экранов

```php
// routes/web.php
Route::middleware('identity')->group(function (): void {
    Route::get('/', DashboardController::class)->name('dashboard');
    // ...остальные экраны продукта
});
```

Истёкшая сессия обрабатывается **штатным механизмом Inertia**: запросы Inertia
не умеют следовать за перенаправлением на чужой домен, поэтому им отдаётся
`409` с заголовком `X-Inertia-Location`, по которому клиент выполняет полный
переход. Собственный перехватчик писать не нужно.

Адрес, на который пользователь шёл, сохраняется и восстанавливается после
входа.

## Разделяемые свойства Inertia

Пакет собирает состав свойств, продукт решает, куда их поставить:

```php
// app/Http/Middleware/HandleInertiaRequests.php
use Verdeect\IdentityIntegration\Inertia\IdentityProps;

public function __construct(
    private readonly IdentityProps $identity,
) {}

public function share(Request $request): array
{
    return [
        ...parent::share($request),
        'identity' => $this->identity->share(),
        // ...собственные свойства продукта
    ];
}
```

Состав `share()`:

```php
[
    'profile' => [            // null, когда сессии нет
        'sub' => '01K...',
        'name' => 'Иванов Иван Иванович',
        'givenName' => 'Иван',
        'familyName' => 'Иванов',
        'middleName' => 'Иванович',
        'locale' => 'ru',
        'shortName' => 'Иван Иванов',
        'initials' => 'ИИ',
    ],
    'crossService' => [       // приходит и без сессии — гостевым набором
        'items' => [/* пункты рейла в порядке отображения */],
        'profileUrl' => 'https://id.example.com/profile',  // пусто у гостя
        'logoUrl' => 'https://id.example.com/installation/logo',
    ],
    'locale' => 'ru',         // язык продукта на этом запросе
]
```

**Токенов здесь нет и быть не может.** Схема Backend-for-Frontend обязательна;
`IdentityProps` — единственное место, где решается, что из identity видит
интерфейс.

**Рейл положен и гостю.** Без сессии `profile` равен `null`, а `crossService`
заполняется гостевым набором установки: до 0.4 продукт отдавал здесь пустую
заглушку и рейл не показывался даже там, где установка его отдаёт.

`profileUrl` у гостя приходит **пустой строкой**, и это значащее значение:
страницы профиля у смотрящего нет. Отличать «не пришло» от «пусто»
потребителю не нужно — показывать в обоих случаях нечего.

Когда установка недоступна, данные рейла **пусты, а не отсутствуют**:
интерфейс различает «рейла нет» и «свойство не пришло», и второе означало бы
ошибку доставки.

`locale` — **язык продукта**, а не установки. У вошедшего язык рейла берётся
из профиля; у гостя профиля нет, и без этого поля компонент рейла откатился бы
на жёсткое умолчание — на англоязычной установке гостевой рейл вышел бы
русским. Язык гостя знает продукт (заголовок `Accept-Language`, кука,
собственное умолчание), а установка о госте не знает ничего и диктовать его
не вправе.

Пункты рейла приходят **уже отфильтрованными по роли**. Своих правил видимости
продукт не применяет: второе правило разошлось бы с первым.

Отрисовку рейла и блока пользователя берёт на себя npm-пакет
[`@verdeect/identity-nav-vue`](https://github.com/smskin/verdeect-identity-nav-vue) —
у него своя документация по встраиванию компонентов.

## Политика содержимого

Логотип установки грузится с чужого домена, форма входа находится на нём же,
а иконки пунктов рейла — **на третьем**: они лежат в объектном хранилище
установки, и адрес у него свой.

```php
// app/Http/Middleware/ContentSecurityPolicy.php
use Verdeect\IdentityIntegration\Support\IconOrigins;
use Verdeect\IdentityIntegration\Support\IdentityOrigin;

public function __construct(
    private readonly IdentityOrigin $identityOrigin,
    private readonly IconOrigins $iconOrigins,
) {}

private function directives(): array
{
    $origin = $this->identityOrigin->resolve();

    return [
        "default-src 'self'",
        'img-src '.implode(' ', array_filter([
            "'self'",
            'data:',
            $origin,
            ...$this->iconOrigins->forSession(),
        ])),
        "form-action 'self' ".$origin,
        // ...остальные директивы продукта
    ];
}
```

`IdentityOrigin::resolve()` возвращает схему, узел и порт без пути.
На незаполненном либо неразбираемом адресе — пустую строку: политика обязана
строиться и на неподнятом окружении. Неразбираемый адрес пишется в журнал
предупреждением — это ошибка настройки.

`IconOrigins::forSession()` возвращает источники иконок текущего пользователя,
без повторов. Адрес берётся **из самих ссылок**, а не из настройки продукта:
настройка задваивала бы знание, и перенос хранилища установкой оставил бы все
продукты с заглушками вместо иконок — молча, потому что заблокированное
изображение выглядит как пункт без иконки. Обращений к установке метод
не делает: к моменту составления заголовка данные рейла уже получены —
разделяемые свойства собираются раньше. Без сессии список пуст.

**Пропустить его нельзя.** Иконка приходит подписанной ссылкой на файл SVG,
и заблокированная политикой она даёт ровно тот же вид, что отсутствующая:
рейл с заглушками из первых букв имён и ни строчки в журнале продукта.

Набор директив пакет не составляет: источники скриптов, стилей и шрифтов
у каждого продукта свои.

## Выход

Кнопка выхода отправляет `POST /auth/logout`. Пакет уничтожает локальную сессию
и токены **до перенаправления**, затем отправляет на `/end-session` установки
с подсказкой `id_token_hint`.

`/end-session` завершает сессию входа целиком, со всеми продуктами установки,
и это требуемое поведение: сотрудник, вышедший на общем компьютере, должен
выйти отовсюду. `/revoke` для выхода не используется — он освобождает токены
одного продукта, не выводя человека из установки, и возврат происходит одним
кликом без пароля.

## Права доступа

Пакет **предоставляет** роль и ограничения учётной записи, но не решает, что
за ними стоит: смысл ролей определяет продукт. Источник один — токен доступа;
`/userinfo` ролей не отдаёт.

### Кто вошёл и что ему можно

`CurrentIdentity` — единственная точка, которой продукт об этом спрашивает.
Разбор токена остаётся внутри пакета.

```php
use Verdeect\IdentityIntegration\Rights\CurrentIdentity;

final class ReportsController extends Controller
{
    public function __construct(private readonly CurrentIdentity $identity) {}

    public function __invoke(): Response
    {
        return Inertia::render('Reports/Index', [
            'reports'   => /* … */,
            'canManage' => $this->identity->allowsWrites(),
        ]);
    }
}
```

| Метод | Отвечает |
|---|---|
| `roles()` | перечень ролей вошедшего |
| `hasRole(string $role)` | есть ли указанная роль |
| `entitlements()` | перечень ограничений |
| `allowsWrites()` | **разрешена ли запись** — этим и принимаются решения |
| `isReadOnly()` | режим «только чтение» — **только для показа человеку** |

**Ничего не запоминайте.** Ни в сессии, ни в свойстве объекта: понижение роли
доезжает истечением токена (стартовое значение — 5 минут) либо сообщением
`user.rights.changed`, и запомненный ответ пережил бы оба. `CurrentIdentity`
читает токен на каждом обращении; обращение дешёвое — токен уже обновлён
посредником `RefreshIdentityToken` в начале запроса.

### Ограничение роли на маршрутах

Посредник объявляется псевдонимом рядом с `identity`:

```php
$middleware->alias([
    'identity'      => RequireIdentitySession::class,
    'identity.role' => RequireIdentityRole::class,
]);
```

Роль называет продукт в самом маршруте:

```php
Route::middleware(['identity', 'identity.role:admin'])->group(function (): void {
    Route::get('/settings', SettingsController::class);
});
```

Несколько ролей через запятую означают «любая из»: `identity.role:admin,user`.

**Порядок существен:** `identity` впереди. У гостя ролей нет, и без требования
входа он получил бы `403` вместо перехода на форму входа — отказ вместо
предложения войти.

### Запрет записи при ограничении

Если продукт поддерживает режим ограниченной работы, посредник вешается
на маршруты **записи**:

```php
$middleware->alias([
    'identity.writable' => DenyWritesWhenRestricted::class,
]);
```

```php
Route::middleware('identity')->group(function (): void {
    Route::get('/reports', ReportsController::class);          // чтение открыто

    Route::middleware('identity.writable')->group(function (): void {
        Route::post('/reports', StoreReportController::class); // запись закрыта
    });
});
```

Белый список маршрутов чтения пакет не ведёт: какие из маршрутов продукта
меняют состояние, знает только продукт. Не поддерживаете режим — просто
не упоминайте посредник.

### Почему не `in_array('read_only', …)`

Перечень ограничений задаёт установка и со временем расширяет. Правило на этот
случай: продукт, встретивший **незнакомое** значение, запрещает все действия,
кроме чтения.

Проверка по конкретному значению этому правилу не отвечает. Ограничение,
добавленное установкой позже, такой продукт не узнает, условие не сработает —
и человек получит полные права. Отказа не будет: прав окажется больше
положенного, а такую ошибку не ловят тестами.

Поэтому `allowsWrites()` выведен из правила: запись разрешена тогда и только
тогда, когда ограничений нет вовсе. Новое ограничение установки закрывает
запись во всех уже развёрнутых продуктах само, без их обновления.

`isReadOnly()` существует ради текста отказа — «ваша учётная запись в режиме
только чтения» понятнее, чем «недостаточно прав» (справка 4.7.4). Решения
на нём принимать нельзя.

### Типовые случаи

Три расклада, которые покрывают почти всё. Псевдонимы ниже считаются уже
объявленными.

**Весь сервис только для администраторов.** Маленький продукт, куда рядовому
сотруднику незачем: одна группа, две строки.

```php
Route::middleware(['identity', 'identity.role:admin'])->group(function (): void {
    Route::get('/', DashboardController::class)->name('dashboard');
    Route::get('/reports', ReportsController::class);
    // …остальные экраны
});
```

**Часть экранов общая, часть административная.** Вложенная группа, новых
классов не нужно:

```php
Route::middleware('identity')->group(function (): void {
    Route::get('/', DashboardController::class);          // всем вошедшим

    Route::middleware('identity.role:admin')->group(function (): void {
        Route::get('/settings', SettingsController::class);
        Route::post('/settings', StoreSettingsController::class);
    });
});
```

**Все читают, пишут не все.** Ограничение учётной записи закрывает запись,
а не экран:

```php
Route::middleware('identity')->group(function (): void {
    Route::get('/reports', ReportsController::class);

    Route::middleware('identity.writable')->group(function (): void {
        Route::post('/reports', StoreReportController::class);
        Route::delete('/reports/{report}', DeleteReportController::class);
    });
});
```

Посредники складываются: `['identity', 'identity.role:admin',
'identity.writable']` означает «вошедший администратор, которому разрешена
запись».

### Скрыть действие в интерфейсе

Посредник отвечает за отказ, а интерфейс — за то, чтобы до отказа не доводить.
Признак отдаётся свойством страницы:

```php
return Inertia::render('Reports/Index', [
    'reports'   => $reports,
    'canManage' => $this->identity->allowsWrites(),
]);
```

```vue
<Button v-if="canManage" :label="t('reports.create')" @click="create" />
```

**Скрытая кнопка разграничением доступа не является.** Она избавляет от
заведомо отказного обращения, и только; сам запрет остаётся за посредником.
Экран без посредника, но со скрытой кнопкой открыт обращением помимо
интерфейса.

### Отказ объясняют человеку

`abort(403)` в посреднике — код ответа, а не готовый экран. Человек, которому
продукт молча ответил «403», идёт в поддержку с «всё сломалось».

Отказ по **роли** и отказ по **ограничению** объясняются по-разному, и для
второго в пакете есть `isReadOnly()` — он затем и заведён:

```php
// bootstrap/app.php продукта
->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->render(function (AccessDeniedHttpException $e, Request $request) {
        $identity = app(CurrentIdentity::class);

        return Inertia::render('Errors/Forbidden', [
            'readOnly' => $identity->isReadOnly(),
        ])->toResponse($request)->setStatusCode(403);
    });
})
```

На экране — «Ваша учётная запись переведена в режим только чтения» либо
«Этот раздел доступен администраторам установки», и в обоих случаях к кому
обратиться. Решения на `isReadOnly()` не принимают: он для текста.

### Прикладные права

Ролей в установке две, и прикладных признаков («диспетчер», «бухгалтер»)
сервис не знает. Такие ограничения продукт обеспечивает у себя — политиками
Laravel, а не этим пакетом. Если политик пока нет, заводите их заглушками,
разрешающими всё: логики они не содержат, их назначение — единственное место
для будущего условия. Проверка прав не размазывается по контроллерам.
